# 健康トラッカー 設計書

最終更新：2026-10-25　／　状態：**案（オーナーの確認待ち）**

この設計書は、今あるアプリ（プロトタイプ）を出発点に、これから作る機能の「形」を先に決めておくためのものです。
各項目に **「なぜこうするのか」** を添えています。実装に入るときは、この設計書のどの章を作るのかを示し、OK をもらってから作ります。

---

## 0. 目的と、設計で大事にすること

| 目的 | 設計で大事にすること |
|---|---|
| ダイエットを**習慣にする** | 記録の手間を最小にする。開いたらすぐ書ける。続いていることが目に見える |
| **PC とスマホで同じデータ**を使う | どちらで書いても、もう一方で同じ記録が見える。片方がオフラインでも記録は失われない |
| **ボタンで簡単に**記録する | 数字の手入力を減らし、「いつもの」をワンタップで入れられる |
| 将来：**バーコードで食品を記録** | 今のうちにデータの形にバーコードの置き場所を用意しておく |

> **なぜ最初に目的を書くのか**：設計で迷ったとき（例：機能を足すか、画面をシンプルに保つか）に、判断の基準になるからです。
> このアプリでは「続けやすさ」を一番に置きます。正確さを上げるために入力が面倒になるなら、続けやすさを優先します。

## 2. 記録項目（データの形）

### 2.1 1日分の記録（今の形を引き継ぐ）

今の形（README の「1日分の記録の形」）は変えずに使います。変えるのは次の2点だけです。

| 追加・変更 | 内容 | 理由 |
|---|---|---|
| `deleted: true` | 記録を消した日は、データを丸ごと消すのではなく「消した」という印を残す | 下の「3.5 削除の伝え方」を参照。印がないと、他の端末に残っている記録で**よみがえってしまう** |
| `updatedAt` を必ず入れる | 今も入っているが、同期で「どちらが新しいか」の判定に使う | 2台で同じ日を書いたとき、新しい方を残すため |

```json
{ "date": "2026-10-27", "deleted": true, "updatedAt": "2026-10-27T22:10:00+09:00" }
```

### 2.2 記録する項目の一覧

| 分類 | 項目 | 入力のしかた | 状態 |
|---|---|---|---|
| 体重 | 体重（0.1kg単位） | 数字。前回の値を初期値に出す | あり |
| 運動 | 種類・時間・強度、歩数 | 種類と強度はボタン | あり |
| 食事 | 時刻・区分・料理名・量・食材とグラム数 | 食材は検索。区分は時刻から自動 | あり |
| 睡眠 | 就寝・起床・昼寝 | 時刻 | あり |
| 水分 | mL | 「＋1杯」ボタン | あり |
| 疲労度・ストレス | 仕事／プライベート 5段階、メモ | ボタン | あり |
| 腹囲 | cm | 数字（`body.waistCm`） | 将来 |
| 食品のバーコード | JAN コード | カメラ or 数字入力 | 将来（4章） |

> **なぜ計算結果（`nutrients`・`kcal`）も保存するのか**：あとで Claude が `health-data` だけを読んで振り返りをするとき、
> 成分表や METs の表がなくても数字がわかるようにするためです。また、将来 METs の値を見直しても、
> 過去の記録の消費カロリーが勝手に変わらない（その日の計算のまま残る）という利点もあります。

### 2.3 マイ食品（バーコードの置き場所を追加）

```json
{
  "id": "my:m1abc23",
  "name": "○○のサラダチキン プレーン",
  "basis": "serving",
  "servingLabel": "1袋",
  "servingGrams": 110,
  "values": { "kcal": 121, "protein": 26.2, "fat": 1.4, "carb": 0.6, "salt": 1.3 },
  "barcodes": ["4901234567894"],
  "updatedAt": "2026-10-27T08:00:00+09:00"
}
```

| 追加 | 理由 |
|---|---|
| `barcodes`（配列） | 同じ商品でも、内容量違いやリニューアルでバーコードが変わることがあるため、1つの食品に複数持てるようにする |
| `updatedAt` | 2台でマイ食品を編集したときに、新しい方を残すため |
| 削除は `deleted: true` の印 | 1日分の記録と同じ理由 |

> **なぜバーコードを「マイ食品」に持たせるのか**：やりたいことは「登録済みの食品なら、読み取るだけで記録」です。
> 市販品は成分表ではなく、パッケージの栄養成分表示で登録する＝マイ食品なので、ここに足すのが一番自然です。
> 新しい入れ物（バーコード表）を別に作るより、データの形がシンプルに保てます。

### 2.4 設定（同期するもの／しないもの）

| 項目 | 同期する？ | 保存先 |
|---|---|---|
| プロフィール、METs、1杯の量 | する | `settings.json` |
| 「いつもの」ボタン（3.2） | する | `settings.json` の `presets` |
| **アクセストークン** | **しない** | その端末の localStorage だけ（別のキー `health-tracker:token`） |
| 最後に同期した時刻、未送信の一覧 | しない | その端末の localStorage |

> **なぜトークンを同期しないのか**：`settings.json` は GitHub に保存されるファイルです。
> トークンをそこに書くと、「金庫の中に金庫の鍵をしまう」ことになり、万一ファイルが見られたときに鍵まで渡ってしまいます。
> トークンは「その端末だけが持つ鍵」として、PC とスマホでそれぞれ入力します。

### 2.5 `schemaVersion`（データの形の版番号）

各ファイルの先頭に `"schemaVersion": 1` を入れます（月のファイルは `{ "schemaVersion": 1, "records": { ... } }`）。

> **なぜ版番号を入れるのか**：今後、腹囲を足すなどで形が変わったとき、アプリが「これは古い形だから読み替えよう」と判断できるからです。
> 今の `normalizeIngredient`（昔の文字だけの食材を読む）と同じ考え方を、ファイル単位でできるようにします。
> ※ `health-data` の README にある月ファイルの形も、6章の「1」を作るときにこの形に合わせて直します。

## 3. 画面

タブは今の4つ（記録・直近7日・マイ食品・設定）のままにします。

> **なぜタブを増やさないのか**：毎日開くのはほぼ「記録」だけです。タブや画面が増えるほど迷いが増え、続けにくくなります。
> 新しい機能は、今ある画面の中の「使う場所」に置きます。

### 3.1 画面ごとの追加

| 画面 | 追加するもの | 理由 |
|---|---|---|
| 全画面の上部 | **同期の状態**（✓ 同期済み ／ ↑ 未送信 ／ ⚠ エラー） | 「スマホで書いた分、PC に届いてる？」を一目でわかるように |
| 記録 | **続けた日数**（例：「12日連続で記録中」） | 習慣化のため。続いていることが見えると、途切れさせたくなくなる |
| 記録・食事 | **「いつもの」ボタン**、**前日と同じ**ボタン | 毎日同じ朝食などを、検索なしでワンタップで入れる |
| 記録・食材検索 | **バーコード**ボタン（将来） | 4章 |
| マイ食品 | バーコード欄（将来）、「いつもの」に登録 | 4章・3.2 |
| 設定 | **同期**（トークン入力・接続テスト・今すぐ同期・最後の同期時刻） | 同期の設定と確認を1か所に |

### 3.2 「いつもの」ボタン（プリセット）

よく食べる料理（例：「朝のヨーグルトとバナナ」）や、よくする運動（例：「ウォーキング30分・普通」）を登録し、記録画面にボタンとして並べます。
押すとその内容が今日の記録に加わります（量はあとで直せる）。

```json
"presets": [
  { "id": "p:1", "kind": "meal", "label": "いつもの朝食", "mealKind": "朝食",
    "items": [{ "name": "ヨーグルトとバナナ", "ingredients": [{ "foodId": "13025", "grams": 100 }, { "foodId": "07107", "grams": 90 }] }] },
  { "id": "p:2", "kind": "exercise", "label": "ウォーキング30分", "type": "ウォーキング", "minutes": 30, "intensity": 2 }
]
```

> **なぜプリセットに栄養値を保存しないのか**：押したときに、その時点の成分表・マイ食品から計算し直すためです。
> マイ食品の値を直したとき、プリセットまで直す必要がなくなります（記録には押した時点の計算結果が残ります）。

### 3.3 続けた日数の数え方

- 「記録がある日」＝ `deleted` でなく、何か1項目でも入っている日（サンプルは除く）。
- 今日まだ記録していなくても、昨日まで続いていれば数を表示（「今日も記録して13日目に」）。

> **なぜ「1項目でも」でよいのか**：完璧に書けない日に「0日に戻る」と、やる気がなくなります。体重だけでも記録すれば続く、くらいのゆるさにします。

## 4. 同期方式（ステップ4）

### 4.1 全体の流れ

```
 スマホ / PC のブラウザ
 ┌────────────────────────┐
 │ アプリ (GitHub Pages)    │
 │  ① まず localStorage に保存 │  ← オフラインでも記録できる
 │  ② GitHub API で送る       │ ──→  health-data（非公開）
 │  ③ 起動時に最新を取ってくる │ ←──   data/2026-10.json など
 └────────────────────────┘
```

| 決めたこと | 理由 |
|---|---|
| **まず端末に保存し、そのあと GitHub に送る**（オフラインファースト） | 電波が悪い場所でも記録が消えない。送れなかった分は「未送信」として覚えておき、次の機会に送る |
| アプリから直接 **GitHub の Contents API** を呼ぶ | サーバーを自分で用意しなくてよい。ブラウザの `fetch` だけで作れ、Web API の学習にもなる |
| ファイルは **月ごと**（`data/YYYY-MM.json`） | 1日1ファイルだとファイルが多すぎ、1年1ファイルだと大きく、2台の保存がぶつかりやすい。月ごとがちょうどよい大きさ。Claude も「先月分」を1ファイルで読める |
| 送るのは**変更があった月のファイルだけ** | 通信量と時間を減らす |

### 4.2 アクセストークン

- **fine-grained personal access token** を使う。
  - 対象リポジトリ：`health-data` だけ
  - 権限：Contents の Read and write だけ（Metadata の Read は自動で付く）
  - 有効期限：つける（例：90日。切れたらアプリが「トークンの期限が切れました」と表示）
- 作り方の手順は、実装の前に画面つきで別途説明します。

> **なぜ権限をここまで絞るのか**：トークンはブラウザに保存するので、万一漏れたときの被害を最小にするためです。
> この設定なら、漏れても触れるのは `health-data` のファイルだけで、他のリポジトリやアカウント設定には触れません。
> 有効期限は「漏れに気づかなくても、いずれ使えなくなる」保険です。
> また、このアプリは外部のライブラリを読み込まないので、他人のコードがトークンを読む心配が少ない、という点もあります。

### 4.3 GitHub API の使い方

| やること | API | ポイント |
|---|---|---|
| ファイルを読む | `GET /repos/toku-origin/health-data/contents/data/2026-10.json` | 中身（Base64）と **`sha`**（そのファイルの版を表す ID）が返る |
| ファイルを書く | `PUT /repos/.../contents/data/2026-10.json` | 中身（Base64）と、**読んだときの `sha`** を送る。1回の保存が1コミットになる |
| ファイルがまだない | GET が 404 | 新しいファイルとして `sha` なしで PUT する |

- 日本語を含む JSON は、`TextEncoder` で UTF-8 のバイト列にしてから Base64 にする（`btoa` だけでは日本語で失敗するため）。
- コミットメッセージは「2026-10-27 の記録を更新」のように、何を変えたかわかるものにする。

> **なぜ `sha` を送るのか**：「私が読んだのはこの版です。この版の上に書きます」という宣言です。
> もし読んだあとに別の端末が先に書いていたら、`sha` が合わず、GitHub が **409 Conflict**（競合）を返して書き込みを断ります。
> これで「知らないうちに、もう一方の端末の記録を上書きして消す」事故を防げます。

### 4.4 2台で保存がぶつかったとき（競合の扱い）

1. PUT が 409 で断られたら、そのファイルをもう一度 GET する。
2. 手元のデータと、GitHub のデータを**日ごとに比べて合成**する。同じ日が両方にあれば、`updatedAt` が新しい方を残す。
3. 合成したものを、新しい `sha` で PUT し直す（最大3回。それでもだめならエラー表示）。

マイ食品も同じく、`id` ごとに `updatedAt` が新しい方を残します。設定はファイル全体で新しい方を残します。

> **なぜ「日ごと」に合成するのか**：PC で昨日の夕食、スマホで今日の朝食を書いた、というよくある場面では、両方とも残ります。
> ぶつかるのは「同じ日を2台でほぼ同時に編集した」ときだけで、そのときは新しい方が残ります。
> 項目ごと（体重だけ・水分だけ）に合成する方法もありますが、仕組みがずっと複雑になる割に、1人で使うアプリではめったに起きないので、まずは日ごとにします。

### 4.5 削除の伝え方

記録を消すときは、データを消さずに `{ "deleted": true, "updatedAt": ... }` に置き換えます（2.1）。

> **なぜ消さずに印を残すのか**：PC で 10/27 を消しても、スマホにはまだ 10/27 が残っています。
> 合成のとき「PC にはない、スマホにはある」だけだと、「スマホで書いたばかりの記録」なのか「PC で消した記録」なのか区別できず、消したはずの記録がよみがえります。
> 「消した」という印と時刻があれば、スマホの記録より新しい削除として正しく扱えます。

### 4.6 いつ同期するか

| タイミング | すること |
|---|---|
| アプリを開いたとき | 今月と先月（直近7日の表示に必要）、`my-foods.json`、`settings.json` を GET して合成 |
| 保存したとき | 端末にすぐ保存 → 数秒待ってから送信（続けて保存したら、まとめて1回送る） |
| 画面を閉じる・隠すとき | 未送信があれば送信を試す |
| 設定の「今すぐ同期」 | 手動で送受信 |
| 送れなかったとき | 「未送信」に残し、次のタイミングで再送 |

> **なぜ数秒待ってから送るのか**：水分の「＋1杯」を3回押すたびにコミットが3つできると、履歴が読みにくくなり、通信も増えるからです。

### 4.7 サンプルとの関係

初回のサンプル記録（`sample: true`）は同期しません。トークンを設定して初めて同期するとき、端末のサンプルは消します。

## 5. バーコード読み取り（将来機能）

### 5.1 やりたいこと

1. 食材検索の「バーコード」ボタンを押す
2. カメラで商品のバーコードを読む（読めないときは数字13桁を手で入力）
3. マイ食品に登録済み → その食品が1個（1食）分、料理に入る
4. 未登録 → マイ食品の登録画面がバーコード入りで開き、栄養成分表示を入力して登録 → 料理に入る
   （2回目からは読むだけで記録できる）

### 5.2 設計の判断

| 決めたこと | 理由 |
|---|---|
| 日本の商品の **JAN コード**（13桁、短縮版は8桁）に対応 | 国内の食品のほとんどに付いている |
| **チェックディジット**（最後の1桁）で読み間違いを確認 | 13桁目は残りの12桁から計算で決まる検算用の数字。合わなければ「読み直してください」と出す |
| まずは**数字の手入力**から作り、そのあとカメラに対応 | 手入力でも「登録済みなら即記録」という一番大事な部分は使える。カメラは端末による差が大きいので、後から足す |
| 外部の商品データベースは**最初は使わない** | 日本の商品の栄養データが揃った無料のものが少なく、値の正確さも確かめにくい。また、何を食べたかを外部に送ることになる。自分で登録した値なら出典（パッケージ表示）がはっきりしている |
| 読み取ったコードは、記録の食材には保存しない | 食材にはすでにマイ食品の `foodId` がある。バーコードはマイ食品側にあるので、二重に持たない |

### 5.3 カメラでの読み取り（実装時に要確認）

- ブラウザの **BarcodeDetector API** を使えばライブラリなしで読めますが、**対応しているブラウザが限られます**（Android の Chrome は対応、iPhone の Safari は未対応という認識ですが、**実装時に MDN の対応表で確認します**）。
- 未対応の端末では、読み取り用のライブラリ（例：ZXing の JavaScript 版）を `vendor/` に置いて使うか、数字入力だけにするかを、そのときに相談します。
- カメラは **HTTPS** のページでしか使えません。GitHub Pages は HTTPS なので、**バーコードは Pages 公開（ステップ5）のあと**に作ります。

> **なぜ今のうちに設計しておくのか**：データの形（`barcodes` の置き場所）を後から変えると、すでに保存したデータの読み替えが必要になります。
> 置き場所だけ先に決めておけば、機能は後からでも足しやすくなります。

## 6. 作る順番

機能ごとにブランチを作り、オーナーの動作確認 → テスト → PR（マージはオーナー）の流れで進めます。

| 順 | 内容 | ブランチ名（案） | 先に必要なもの |
|---|---|---|---|
| 1 | データの形の準備（`schemaVersion`、削除の印、マイ食品の `updatedAt`） | `feature/data-format-v1` | なし |
| 2 | **同期**（ステップ4） | `feature/sync` | 1、トークン |
| 3 | **GitHub Pages で公開**（ステップ5） | `feature/pages` | 2 |
| 4 | 「いつもの」ボタン・前日と同じ・続けた日数 | `feature/quick-record` | 1 |
| 5 | バーコード（数字入力） | `feature/barcode-input` | 1 |
| 6 | バーコード（カメラ） | `feature/barcode-camera` | 3、5 |
| 7 | 腹囲、Claude による週次振り返り | その時に決める | 2 |

> **なぜデータの形の準備を最初にするのか**：同期を始めると、データが2台と GitHub の3か所に広がります。
> 広がったあとに形を変えるより、広がる前に整えておく方がずっと楽で安全です。
> **なぜ同期を「いつもの」ボタンより先にするのか**：PC とスマホで同じデータを見られないと、実際の生活で使い始められないからです。使い始めてから、どこが面倒かを見て入力の工夫を足す方が、本当に必要なものを作れます。

## 7. 練習課題の候補（学習用）

小さく、テストで正解を確かめやすいものを選びました。実装のときに「やってみますか？」と声をかけます。

1. **JAN コードのチェックディジット**を計算する関数 `janCheckDigit("490123456789")` を書く（5章）。
2. 日本語を含む文字列を **Base64 に変換**する関数を書き、`atob` で戻して一致するか確かめる（4.3）。
3. 2つの月データを `updatedAt` で**合成する関数**のテストケースを考える（4.4。「片方だけにある日」「両方にある日」「片方で削除した日」）。
